## 1. 这是什么（30 秒版）

**一个能在本地跑起来的、带记忆和工具的 AI 聊天 Agent。**

用户在一个浏览器聊天窗口（或命令行）里跟商汤日日新对话。它能**记住这个会话聊过什么**
（重启后还在），会**调用工具**（算数、查时间、查你的本地文档、读写你的文件），能
**看图回答**，还能**同时开好几个话题互不打断**。所有数据都落在你自己的硬盘上，
不走任何第三方。

```
┌──────────────────────────────────────────────────────────┐
│  用户（浏览器 / 命令行）                                    │
│        │                                                 │
│        ▼                                                 │
│  对话 → 有记忆 → 会调工具 → 会查你的文档 → 能看图 → 多话题并行 │
│        │                                                 │
│        ▼                                                 │
│  数据全在本机：会话历史 / 知识库 / 日志 / MCP 工作目录         │
└──────────────────────────────────────────────────────────┘
```

**关键数字**（都是实测，不是估的）：

| 项          | 值                                                                                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Python 源码 | **1,888 行**（16 个非空模块，19 个 `.py`）                                                                                  |
| 前端        | **345 行**（单个 `index.html`，无框架、无构建）                                                                             |
| 测试        | **2,342 行 / 13 个测试文件 + `conftest.py` / 142 个用例**，全 mock、不联网、不花额度                                        |
| 辅助脚本    | **1,631 行 / 19 个**（`e2e_*` 端到端、`probe_*` 真机探针、`spike_*` 技术验证）                                          |
| 第三方依赖  | **8 个**（`openai` / `fastapi` / `uvicorn` / `pydantic-settings` / `fastembed` / `mcp` / `httpx` / `pytest`） |
| 里程碑      | **M1~M8 全交付**，12 份文档，路线图全绿                                                                                       |
| 响应延迟    | 中位 **7.6s**，最久实测 **78s**（reasoning 模型思考，非网络问题）                                                       |
| 空回复      | 生产配置下 **35 次真实调用 0 空**；发生时抛明确异常而非静默留脏数据                                                           |
| 运行要求    | Python 3.11+，Windows 11 已验证，跨平台未验证                                                                                       |

## 3. 使用方法

### 3.1 第一次跑起来

```bash
# Windows（推荐）：双击 scripts\setup.bat
# 然后编辑 .env，把 SENSENOVA_API_KEY 换成你的真实 Key
# 其他配置项都有默认值，可以不改

call venv\Scripts\activate.bat
python -m src.api    # Web 界面 → 浏览器打开 http://localhost:8000
python -m src.cli    # 命令行聊天
```

Linux / macOS 用手动步骤（`setup.bat` 只在 Windows 11 验证过）：

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # 填 SENSENOVA_API_KEY
python -m src.api
```

首次启动**自动新建一个会话**；之后每次启动**自动继续最近一次会话**。

### 3.2 CLI 命令

```
/exit         退出
/help         帮助
/new          新建会话（旧会话留在磁盘，可随时切回）
/sessions     列出所有会话（id / 更新时间 / 条数 / 首句预览 / 是否已摘要）
/use <id>     切换到指定会话
/delete <id>  删除会话（不可恢复）
/clear        清空当前会话历史
/ingest       重新摄入知识库文档
```

其余输入一律当作对话内容发给模型。

### 3.3 Web 界面

左侧会话列表（新建 / 切换 / 删除），右侧对话区。粘贴或点 🖼️ 上传图片（支持多张）。
**切换会话只切显隐、不销毁视图**——所以切走时正在生成的回复继续在跑，切回来还在流。

### 3.4 配置项（`.env`）

默认值都能直接跑，下面按重要程度列，完整注释在 `.env.example`。

| 项                                                                           | 默认                                                                              | 说明                                                  |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `SENSENOVA_API_KEY`                                                        | —                                                                                | **必填**，唯一没有默认值的项                    |
| `SENSENOVA_MODEL`                                                          | `sensenova-6.8-flash-lite`                                                      | OpenAI 协议兼容                                       |
| `MAX_TOKENS`                                                               | 留空                                                                              | ⚠ **建议留空**。这是本项目最反直觉的一项，见下 |
| `SESSION_DIR`                                                              | `data/sessions`                                                                 | 会话历史                                              |
| `SUMMARY_KEEP_TURNS` / `SUMMARY_MAX_CHARS`                               | `20` / `1500`                                                                 | 保留几轮原文，更早的压成摘要                          |
| `KNOWLEDGE_DIR` / `CHUNK_SIZE` / `CHUNK_OVERLAP` / `RETRIEVAL_TOP_K` | `data/knowledge` / `400` / `50` / `4`                                     | RAG                                                   |
| `MCP_SERVER_COMMAND` / `MCP_SERVER_ARGS` / `MCP_ALLOWED_DIR`           | `npx` / `-y @modelcontextprotocol/server-filesystem` / `data/mcp_workspace` | MCP                                                   |
| `LOG_LEVEL` / `LOG_DIR`                                                  | `INFO` / `data/logs`                                                          | 日志                                                  |

**`MAX_TOKENS` 为什么建议留空**（这个坑值得记一次）：

`sensenova-6.8-flash-lite` 是 reasoning 模型，输出分两部分——`reasoning`（思考过程，
计数进 `completion_tokens`）和 `content`（最终答案）。**如果 `MAX_TOKENS` 小于模型实际
需要的思考量，思考会吃掉整个预算，`content` 就是空的。**

实测（`docs/11` §7 发现三）：

```
MAX_TOKENS=50     → 100% 空回复
MAX_TOKENS=2048   → 67% 空回复
MAX_TOKENS=4096   → 0%
不传 MAX_TOKENS    → 0%（服务端默认上限够，实测放行过 completion=8567 且未截断）
```

而且思考消耗是**服务端随机抖动**的：同一句 60 字提问，`reasoning_tokens` 从 70 跑到 8533。
所以结论是**留空让服务端自己定**，显式设一个较低的值反而更容易出事。

## 4. 全景架构

### 4.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│  ① 入口层（可替换的壳，两条并列，共用同一套核心）                 │
│                                                             │
│     src/cli.py                src/api.py                    │
│     命令行循环                  FastAPI + SSE + static/       │
│        │                          │                         │
│        └──────────┬───────────────┘                         │
│                   ▼                                         │
│  ② 组装层                                                   │
│     src/bootstrap.py    ← 配置 / provider / agent /         │
│                           memory / retriever 都在这装到一起   │
│                   │                                         │
│                   ▼                                         │
│  ③ 编排层（唯一入口，CLI 和 Web 都不越过它）                   │
│     src/core/service.py  ChatService                        │
│     会话管理 · 历史组装 · 截断 · 摘要 · 锁 · 失败撤回 · 落盘     │
│                   │                                         │
│                   ▼                                         │
│  ④ 执行层                                                   │
│     src/core/agent.py  ChatAgent                            │
│     有工具 → ReAct 循环（complete_stream）                  │
│     无工具 → 流式直答（chat_stream）                        │
│      │                       │                              │
│      ▼                       ▼                              │
│  ⑤ 工具层              ⑥ 联网层                              │
│     src/core/tools.py     src/core/provider.py              │
│     ToolRegistry（抽象）    BaseProvider（抽象接口）           │
│      ├─ 内置：计算器/时间       src/providers/sensenova.py    │
│      ├─ RAG：search_kb         （openai SDK + 重试 + 空回复检测）│
│      └─ MCP：wrap_mcp_tools                                       │
│     src/core/mcp.py         ⑦ 记忆层                          │
│     src/core/rag.py         src/core/memory.py MemoryStore   │
│     src/core/embeddings.py  src/core/models.py 数据模型       │
│                                                             │
│  ⑧ 基础设施  src/config.py（.env 单例）· src/core/logger.py │
└─────────────────────────────────────────────────────────────┘
```

**这张图最重要的一件事**：CLI 和 Web 是**并列的壳**，不是前后关系。两者都只调
`ChatService` 这一个入口，都不直接碰 Agent、Memory、Provider。所以**加第三种入口
（桌面端、微信、Telegram）只需要复制一层壳**，核心一行不用动。

### 4.2 依赖方向（谁 import 谁）

```
config.py ───────────────────────────────────────────────────┐
                                                             │
cli.py ───┐                                                  │
          ├──▶ bootstrap.py ──▶ service.py ──▶ agent.py ──▶ provider.py ◀── models.py
api.py ───┘        │                │              │              │
                   │                │              ▼              ▼
                   ├──▶ memory.py ◀─┘        tools.py      sensenova.py
                   │                │              │
                   ├──▶ rag.py      │              ├─▶ rag.py
                   │       │        │              └─▶ mcp.py
                   └───────┴────────┴──▶ embeddings.py
                                    
logger.py ◀── 被 service / sensenova / bootstrap 共同使用（无人 import 反向）
utils.py  ◀── 被 agent / sensenova 共同使用
```

**读法**：箭头只往右（往下）指，没有回路。最底层的 `models.py`、`provider.py`、
`utils.py`、`config.py` 不 import 任何业务模块——**这是能全 mock 测试的前提**：
想测 `service`，就注入一个假的 provider，一次 API 都不用发。

### 4.3 三个可替换的边界

| 边界            | 抽象                      | 现在谁实现                        | 换掉要动哪里                                         |
| --------------- | ------------------------- | --------------------------------- | ---------------------------------------------------- |
| 换模型 / 换厂商 | `BaseProvider`          | `SenseNovaProvider`             | 写一个新类 + `bootstrap.build_service` 里改一行    |
| 换向量模型      | `Embedder`              | `FastembedEmbedder`（本地 BGE） | 写一个新类 + `build_retriever` 里改一行            |

这就是 `docs/01` §2 那句「分层 + 接口先行」的实际回报。

## 5. 时序图：一条消息的完整旅程

这是全项目最值得看的一张图。看完它，整个系统的行为就都清楚了。

### 5.1 主路径（无工具，最简）

```
用户      前端                api.py            ChatService            ChatAgent          SenseNovaProvider        商汤服务端
 │ 点发送   │                     │                  │                     │                     │                    │
 │─────────▶│ POST /sessions/{id} │                  │                     │                     │                    │
 │         │ /messages            │                  │                     │                     │                    │
 │         │────────────────────▶│                  │                     │                     │                    │
 │         │                     │ ① service.send() │                     │                     │                    │
 │         │                     │─────────────────▶│                     │                     │                    │
 │         │                     │                  │ ② 抢会话锁 (≤30s)    │                     │                    │
 │         │                     │                  │    抢不到 → SessionBusyError → 409         │                    │
 │         │                     │                  │                     │                     │                    │
 │         │                     │                  │ ③ memory.load(id)   │                     │                    │
 │         │                     │                  │ ④ conv.add(USER)    │                     │                    │
 │         │                     │                  │ ⑤ _build_context    │                     │                    │
 │         │                     │                  │    system_prompt     │                     │                    │
 │         │                     │                  │    + 当前时间         │                     │                    │
 │         │                     │                  │    + 对话摘要（如有）  │                     │                    │
 │         │                     │                  │    + 截断后的历史      │                     │                    │
 │         │                     │                  │ ⑥ agent.respond()   │                     │                    │
 │         │                     │                  │────────────────────▶│                     │                    │
 │         │                     │                  │                     │ 无工具 → chat_stream  │                    │
 │         │                     │                  │                     │────────────────────▶│ POST /chat        │
 │         │                     │                  │                     │                     │  (stream=True)     │
 │         │                     │                  │                     │                     │───────────────────▶│
 │         │                     │                  │                     │◀───── chunk ────────│◀──── chunk ────────│
 │         │                     │                  │◀──── chunk ─────────│                     │                    │
 │         │                     │◀── SSE ─────────│                     │                     │                    │
 │         │◀─ data: {delta} ────│                  │                     │                     │                    │
 │◀─ 逐段显示─│                     │ (重复多次)         │                     │                     │                    │
 │         │                     │◀─ data: [DONE] ─│                     │                     │                    │
 │         │◀─ [DONE] ───────────│                  │                     │                     │                    │
 │         │                     │                  │ ⑦ conv.add(ASSISTANT)│                     │                    │
 │         │                     │                  │ ⑧ _maybe_summarize（可能触发滚动摘要）        │                    │
 │         │                     │                  │ ⑨ memory.save() ← 原子写，成败都落盘          │                    │
 │         │                     │                  │ ⑩ release 锁         │                     │                    │
 │         │                     │                  │ [请求结束 耗时=X.XXs] │                     │                    │
```

**10 步里最关键的三个**：

- **② 锁在生成之前就抢**。不是"回复完了再锁"。这保证同一会话的两条消息排队而不是互相覆盖。
- **⑨ 无论成败都落盘**。这行在 `finally` 里，是"历史永远有问有答"这个承诺的落点。
- **⑤ 当前时间是每轮现算的**。它不能写死在 `system_prompt` 里（那份是进程启动时定死的，
  跑一晚上就过期了），所以在 `_build_context` 里按轮生成。见 §9 决策 6。

### 5.2 有工具时的 ReAct 循环

```
ChatService                ChatAgent                    SenseNovaProvider
     │                        │                              │
     │── respond(context) ───▶│                              │
     │                        │  ① complete(msgs, tools)    │
     │                        │─────────────────────────────▶│
     │                        │◀── finish_reason="tool_calls"│
     │                        │    tool_calls=[calculator]   │
     │                        │                              │
     │                        │  ② 把这次调用记成 assistant 消息，塞回历史
     │                        │  ③ 本地执行 calculator("123*45")  ← 不走网络！
     │                        │  ④ 把结果记成 tool 消息，塞回历史
     │                        │                              │
     │                        │  ⑤ 再问一次 ────────────────▶│
     │                        │◀── finish_reason="stop"     │
     │                        │    content="结果是 5535"     │
     │                        │                              │
     │◀─ _chunked(每16字一段) ─│  ⑥ 最终答案切小段 yield，让 SSE 逐段推
     │                        │                              │
     │      循环上限 5 轮；到顶还没拿到答案就用最后一次 content 兜底
```

**三个容易看错的点**：

1. **工具是本地执行的**，不走网络往返。模型只负责"决定调什么、传什么参数"。
2. **工具循环现在也是真流式的**（`docs/16`）。正文在每一轮里逐 token 往外吐；
   工具决定要等整轮流完才知道（参数是分段的 JSON 片段，必须攒齐才解析得出），
   但这不挡正文——最终答案那一轮照样逐 token 出字。改造前的做法与理由见 `docs/10`。
3. **工具调用那一轮没有正文**。所以「首字耗时」里包含「想 + 调工具 + 再想」，
   工具轮结束前屏幕上什么都不会有。改造把长回复的首字从 2.75s 降到 1.20s（458 字实测）。

### 6.2 会话锁状态（M7 的核心）

```
                 ┌─────────────────────────────────────┐
                 │        ChatService._locks            │
                 │   dict[session_id] → threading.RLock │
                 │   （每个会话一把独立的锁）              │
                 └─────────────────────────────────────┘
                        ▲              ▲
                        │              │
              会话 A 的消息        会话 B 的消息
              (正在生成)           (同时在生成 ✅)
                        │
                        ▼
              会话 A 的第二条消息
              ┌────────────────────┐
              │ 30s 内能等到 → 排队   │  正常生成，只是晚一点
              │ 30s 等不到 → 409    │  "会话正在生成回复，请稍候再发"
              └────────────────────┘

              清空/删除（housekeeping）
              ┌────────────────────┐
              │ 等 5s 就放弃        │  不让"点一下删除"卡半分钟
              │ 等不到 → 409        │
              └────────────────────┘
```

**为什么要两档超时**：发消息等 30s 是因为生成本身可能就要几十秒，值得等；
清空/删除只是删数据，5s 还没等到就说明在生成中，不如直接告诉用户"等会儿再删"。

**锁管不到的**：Python 线程锁管不到另一个进程。同时开 CLI 和 Web 共享同一个
`SESSION_DIR` 是有风险的（见 `docs/10` §10.2，本项目判为不做多进程隔离）。

### 7.4 三处最容易误读的地方

1. **`ChatService` 既是门面也是编排器**。它调 `agent.respond`，也调 `memory.load/save`，

## 8. 数据与持久化

### 8.1 数据存在哪

```
项目根/
├── .env                        ← API Key（gitignore，永不提交）
├── data/
│   ├── sessions/*.json         ← 会话历史（gitignore）★ 唯一真正的用户数据
│   ├── knowledge/*.md|.txt     ← 你的知识库文档
│   ├── logs/agent.log          ← 日志 + agent.log.1/.2/.3 轮转（gitignore）
│   └── mcp_workspace/          ← MCP filesystem 服务器的授权目录
├── venv/                       ← 虚拟环境（gitignore）
└── .pytest_cache/              ← 测试缓存
```

**删掉 `data/sessions/` = 删掉所有对话历史**，没有备份机制。

### 8.2 三种数据的写法和安全性

| 数据      | 写入方式                                           | 崩溃时会不会坏               |
| --------- | -------------------------------------------------- | ---------------------------- |
| 会话 JSON | 写临时文件 → `fsync` → `os.replace` 原子替换 | **不会**，替换是原子的 |
| 日志      | `RotatingFileHandler`，1MB 轮转保留 3 份         | 不会，日志本来可丢           |
| 知识库    | **纯内存**，启动时摄入                       | 重启后重新摄入（不写缓存）   |

会话写入的完整保护（`MemoryStore._atomic_write`）：

```python
tmp = path.with_name(f"{path.name}.{os.getpid()}.{threading.get_ident()}.tmp")
json.dump(...) → flush() → os.fsync()     # 保证落盘，不是只进内存
os.replace(tmp, path)                      # 原子替换，不会出现半截 JSON
except PermissionError: sleep(0.02 * n)    # 文件被别处占用时重试 3 次
```

临时文件名带 `pid` + `thread`，避免并发写同名临时文件互相覆盖。

### 8.3 隐私设计：日志记什么、不记什么

**承诺：日志只记元数据，永远不记消息正文。**

```
data/logs/agent.log 里你会看到：
  2026-09-30 14:02:11 INFO    agent.service: 请求开始 id=20260908-153000 输入=32字
  2026-09-30 14:02:18 INFO    agent.service: 请求结束 id=20260908-153000 耗时=6.84s
  2026-09-30 14:05:02 WARNING agent.provider: 空回复: max_tokens=50 reasoning_tokens=50 ...

你会看不到：
  用户到底问了什么、模型答了什么
```

理由：会话历史已经完整落盘到 `data/sessions/`，日志重复记录既膨胀又没必要
（而且会让日志文件本身变成隐私泄露点）。

这条承诺是**用测试锁住的**，不是靠约定——`test_message_body_never_logged`
构造了一段极不可能随机出现的正文，断言它不在日志里。

## 9. 关键设计决策一览

按影响面从大到小。每条都有出处，想深入再回去看那期文档。

| #  | 决策                                                                    | 为什么                                                                                                                                           | 出处                       |
| -- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------- |
| 1  | **不用 LangChain，直接 openai SDK**                               | MVP 只需"消息→模型→回复"，LangChain 抽象排障更难；生产级 agent 主流是"薄封装 + 原生 SDK"，依赖越少越好升级                                     | `docs/01` §4            |
| 2  | **分层 + 接口先行**                                               | 换模型只写一个类；加第三种入口只复制一层壳。**加功能时内核不用动，改运维问题时核心也不用动**                                               | `docs/01` §2            |
| 3  | **会话历史用 JSON 文件，不上数据库**                              | 单用户本地产品，文件可读可 grep 可手改；`os.replace` 原子替换保证不坏                                                                          | `docs/03`                |
| 4  | **同一个会话串行，不同会话并行**                                  | 直接并发会让两个请求读同一份旧快照、各自落盘互相覆盖——用户消息被静默丢掉。**宁可报 409，也不要写坏历史**                                 | `docs/10`                |
| 5  | **失败时撤回本轮用户消息再落盘**                                  | 保证磁盘上的历史永远是"有问有答"的完整对话，不会留下有问无答的脏记录                                                                             | `docs/11`                |
| 6  | **当前时间每轮现算，不写死在 system_prompt**                      | 修一个真实 bug：时间回答会烂在历史里，模型再被问"现在几点"时直接复读几天前的旧答案                                                               | `docs/10`                |
| 7  | **摘要滚动压缩，不用截断**                                        | 截断会真丢信息；滚动摘要始终有界——只总结"旧摘要 + 新溢出的一段"，不随对话长度膨胀                                                              | `docs/09`                |
| 8  | **RAG 用纯 Python 暴力余弦，不上 FAISS**                          | 本地几十上百个 chunk 量级，零依赖最好懂；规模大了换 FAISS **接口不变**                                                                     | `docs/05`                |
| 9  | **MCP 用后台线程 + 常开事件循环 + `run_coroutine_threadsafe`**  | MCP 是 asyncio，我们的 `Tool.func` 是同步函数。这是唯一干净的桥接方式                                                                          | `docs/07`                |
| 10 | **计算器用 AST 白名单求值，不用 `eval`**                        | 只放行四则运算 + 括号 + 正负号。模型生成的表达式可能被注入，`eval` 是任意代码执行                                                              | `docs/04`                |
| 11 | **空回复抛异常，不重试**                                          | spike 证明根因是 `max_tokens` 被 reasoning 耗尽，回退非流式也没用——同样的预算还是会耗尽。**重试等于在服务端行为上押注**                | `docs/11` §7 发现三     |
| 12 | **不重试这件事被测试锁住**                                        | `test_empty_reply_not_retried` 断言 API 只被调了 1 次。半年后有人想加自动重试，它会第一个红                                                    | `docs/11` §9            |
| 13 | **日志挂 root，不挂 `agent` 命名空间**                          | 任何模块的日志都落文件，不用逐处 propagate；pytest 的 `caplog` 天然能捕获                                                                      | `docs/11` §5.4          |
| 14 | **第三方 SDK 日志降级到 WARNING**                                 | 否则每次请求都在日志里刷一行 `httpx2: HTTP Request ...`。**坑**：openai 3.3.1 用的 logger 名叫 `httpx2` 不是 `httpx`，按常识写会失效 | `docs/11` §7 发现六     |
| 15 | **工具循环走非流式，最终答案 `_chunked(16)`（docs/16 已推翻）** | 当时的前提是「服务端本来就把整段算完才下发」——这个前提**只对商汤成立**。换 DeepSeek 后真逐 token，流式工具循环重新值得做                 | `docs/10` → `docs/16` |
| 16 | **RAG / MCP 失败时静默降级，不阻塞启动**                          | 没装 fastembed / 没装 Node.js 时，聊天照常，只是少了检索和外部工具。只打一条 warning                                                             | `docs/07`                |
| 17 | **MAX_TOKENS 默认留空**                                           | reasoning 消耗是服务端随机抖动（70~8533），显式设一个低值等于把预算砍到低于服务端默认上限，比留空更容易空回复                                    | `docs/11` §7 发现三     |

### 10.2 三个最值钱的技巧

1. **用 mock client 验证 provider 行为，一次 API 都不花**
   `p._client.chat.completions.create.return_value = iter(_stream_chunks([]))`
   ——把"12 个空 chunk"直接喂进去，空回复就稳定复现了，不用靠 36% 的随机率碰运气。
2. **决策用守卫测试锁住**
   `test_empty_reply_not_retried` 断言 API 只被调了 1 次——把"不重试"这个决定
   **变成可执行的红绿灯**，而不是文档里的一句话。
3. **隐私属性用"不可能随机出现的正文"断言**
   构造 `"这是一段极不可能随机出现的秘密正文 XXXXZZZZ9999"`，然后断言它**不在日志里**。
   这是"记什么/不记什么"这条设计承诺的可执行化。

### 10.3 没覆盖到的

诚实说两条（`docs/11` §10.3）：

- **跨平台部署只验过 Windows**。Linux/macOS 没人真跑过。
- 日志轮转的机制已验过（`maxBytes` patch 到 512 真触发 33 次轮转），
  但生产阈值的 1MB 本身只验了配置值等于 1048576。

## 11. 已知边界（明确做不了的，不是遗漏）

| 项                         | 状态                | 为什么                                                                                                                                                                                    |
| -------------------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 语音输入                   | ❌ 不做             | 输入不在延迟瓶颈上（响应中位 7.6s、最久 78s，输入只占两三秒）；且 `webkitSpeechRecognition` 不支持 Firefox                                                                              |
| 部署到公网                 | ⛔ 另一块工作       | 当前准确状态是**「本地一键跑起的个人产品」**，不是「能上线到服务器的产品」。要上公网需认证、限流、进程守护、密钥管理——`docs/01` 的 M8 原始范围（部署/监控/认证/合规）就是这份待办清单 |
| 用户认证 / 合规            | ❌ 不需要           | 跑在 `127.0.0.1`，没有"他人"要挡                                                                                                                                                        |
| 多实例 / 跨进程隔离        | ❌ 不需要           | 本地只有一个进程拥有会话目录                                                                                                                                                              |
| 并发上限 / 限流            | ❌ 本期限定         | 单用户没有打爆系统的场景；30s `busy_timeout` 已挡住同会话连点                                                                                                                           |
| 性能优化（async / 连接池） | ❌ 不需要           | 瓶颈在服务端，不在客户端                                                                                                                                                                  |
| 摘要挪到后台线程           | ❌ 不做             | 风险大于收益（摘要失败会污染历史，收益是省下几百毫秒）                                                                                                                                    |
| 空回复根因修复             | ❌ **不可能** | 根因在服务端（reasoning 模型），客户端只能处理、不能修好                                                                                                                                  |
| 空回复自适应探测           | ❌ 过度工程         | 服务端行为不可预测（延迟 4s~52s，空回复率 0%~100%），写自适应逻辑等于在服务端行为上押注                                                                                                   |
| 多 Agent 编排              | ⛔ 另立山头         | 超出这个项目的定位                                                                                                                                                                        |
| 真流式打字机               | ❌ 无收益           | 服务端先把整段算完再下发，代码已做到位（`stream=True` + 逐块刷新）。要真流式得换支持流式吐 token 的模型/服务商                                                                          |

**一句话**：这个项目不是"半成品"，是**一个范围已经判清楚的完整产品**。
上面每一项都有理由，不是没时间做。

## 13. 扩展指南：加个东西从哪下手

按你想加的东西类型，直接给位置。

### 13.1 换模型 / 加个新厂商

```python
# 1. 写一个新 provider（照抄 sensenova.py，改 base_url 就行）
class QwenProvider(BaseProvider):
    def chat(self, messages): ...
    def chat_stream(self, messages): ...
    def complete(self, messages, tools=None): ...

# 2. bootstrap.py 的 build_service 里改一行
provider = QwenProvider(...)
```

**ReAct 循环、记忆、界面、测试全都不用动**——因为 `BaseProvider` 是唯一的耦合点。

### 13.2 加一个新工具（最常见的需求）

```python
# src/core/tools.py 里，在 build_default_tools 中加一个 registry.register(...)
registry.register(Tool(
    name="get_weather",
    description="查询某地天气。当用户问天气时调用。",
    parameters={
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"],
    },
    func=lambda city: fetch_weather(city),   # 返回字符串
))
```

就这一处。**不用碰 agent、service、api、cli、前端。** 加完写个 `test_tools.py` 的用例。

### 13.3 加第三种入口（桌面端 / 微信 / Telegram）

```python
# 复制 cli.py 或 api.py 的壳，只调 build_service() + service.send()
from src.bootstrap import build_service
service = build_service()
for chunk in service.send(session_id, "你好"):
    ...
```

核心一行不用动。这就是分层架构的红利。

### 13.4 加新配置项

```python
# 1. src/config.py 的 Settings 里加字段
my_feature_flag: bool = True
# 2. .env.example 里加注释行（保持同步！）
# 3. tests/test_config.py 加一个用例
```

### 13.5 改历史压缩策略

在 `ChatService._trim` 和 `_maybe_summarize` 里改。两个上限：
`max_turns`（轮数）和 `max_chars`（字符）。**注意**：`max_turns` 不能小于
`summary_keep_turns`，`ChatService.__init__` 里已强制抬平——
否则会出现"还没进摘要、又被截断"的中间那几轮被静默丢掉。

### 13.6 加新测试

```bash
python -m pytest tests/test_xxx.py -q     # 只跑新文件
python -m pytest -k "关键词" -q            # 按名字筛
```

**原则**：能用假 provider / mock client 就绝不发真实请求。
花额度的脚本统一放 `scripts/`（`e2e_*` / `probe_*` / `spike_*`），**不进 `tests/`**。

### 13.7 写新文档

沿用 `docs/01`~`11` 的体例：**实测数字必须真跑**、**结论必须诚实**（写不出
"已达成"就写"有条件地未验证"）、**判掉的东西也要记下来并给出理由**。
最后一句话总结收在文末。

**这个项目的真实状态**：

```
┌─────────────────────────────────────────────────────────────┐
│  能干什么：对话 · 记忆 · 多会话 · 工具 · RAG · MCP · 图片 · 并发    │
│                                                            │
│  质量：1,888 行源码 / 142 个测试全绿 / 6.7s 跑完              │
│  可靠性：失败不静默、不写脏数据、日志可查                        │
│  架构：分层 + 三个可替换边界，加功能不动内核                     │
│                                                            │
│  不是：半成品、能演示的 demo、"差一点就能上线"的项目              │
│  是：  一个范围判清楚的、本地可用的完整产品                      │
└─────────────────────────────────────────────────────────────┘
```

**下一步**不是加功能，是**用它几周**——让这个产品的痛点从真实使用里冒出来，
而不是凭想象排下一期。要上公网的话，`docs/01` 的 M8 原始范围就是那份待办清单。

**一句话总结**：**这个项目是一个「本地个人 AI Agent」**——
M1 造了会说话的大脑，M2 配了笔记本，M3 装了电话（工具），M4 接了资料室秘书（RAG），
M5 把电话线换成了标准接口（MCP），M6 给了它眼睛，09 给了它压缩更早记忆的能力，
M7-a 让它能同时应付多个话题，M8 请来了值班员（日志 + 空回复检测）。
**骨架是「分层 + 接口先行」**：CLI 和 Web 是两个并列的壳，都只调 `ChatService` 这一个入口；
往里读是 ReAct 循环 + 联网层，往外是三个可替换的边界（换模型 / 换向量模型 / 加工具），
底下是会话 JSON 原子写 + 只记元数据的日志。
**1,888 行代码换来的是：加功能时内核不用动，改运维问题时核心也不用动。**
