# 16 流式工具循环：正文逐 token，工具决定在每轮收尾时读出

> **改了什么**：工具循环从「非流式 `complete()` + 事后 `_chunked(16)` 假打字机」换成
> `complete_stream()` —— 每一轮都真流式，正文边到边吐，工具调用在整轮流完之后才读出来。
>
> **为什么现在才做**：`docs/09` §9.2 判掉这件事的理由是「服务端本来就把整段算完才下发，
> 改流式用户照样等 166 秒」。那个前提**只对商汤成立**。`docs/14` 换到 DeepSeek 后实测
> 真逐 token（610 字 437 段，首 token 0.74s），`docs/10` 里就留了那句
> 「换到 DeepSeek 后流式工具循环重新变得值得做」。本文档是那句的兑现。
>
> **时间和条件**：2026-10-15，Windows 本地，`deepseek/deepseek-chat`，
> `openai` 3.3.1，Python 3.414。§6 的数字全部由 `scripts/spike_stream_tools.py`
> 和 `scripts/e2e_stream_tools.py` 真跑得出。

---

## 1. 结论先行

**改动前**（Web 端的实际观感，`docs/06` 自己记过）：
> 「M3 之后工具始终注册，`respond()` 走非流式 `complete()` 循环，所以 `service.send()`
> 实际是一次性 yield 整段。Web 端看到的是『思考中… → 整段出现』，不是打字机。」

注意这句话覆盖面比当时以为的更大：**M3 之后所有回复都不是流式的**，不只是「需要调工具
的那些」——因为工具始终注册，`if not schemas` 那个分支在生产环境里一次都走不进去。

**实测对比**（同一台机器、同一个模型、同一天，`scripts/e2e_stream_tools.py`）：

| 场景 | 改动前 | 改动后 |
| --- | --- | --- |
| 长回复（458 字）首字耗时 | **2.75s**（等到整块返回） | **1.20s** |
| 长回复（458 字）拿到全文 | 2.75s | 3.99s（但前 1.20s 就在出字） |
| 正文分段数 | 1 个整块 | **318 段**，单段最大 4 字 |
| 短回复（21 字）首字耗时 | ~2.7s | 2.76s（**没变化**，见 §7.1） |
| 短回复分段数 | 1 个整块 | 10 段，答案轮 0.12s |

一条必须先说清的代价：`docs/14` 实测不带工具时首 token 0.74s，带上工具 schema 后是
1.20s。**工具 schema 参与 prefill，慢约 0.4s**。这是流式换来的账，不是白拿的。

## 2. 探针：DeepSeek 到底支不支持「流式 + 工具」

改造前只有推测。`scripts/spike_stream_tools.py` 跑了 3 组真实调用，回答三个问题。

### 2.1 `stream=True` 和 `tools=` 能不能同时下发

**能**，没有 400。这是前置条件——如果不行，整个工具路径只能退回非流式。

### 2.2 工具参数怎么到达

**分段到达，而且切得很碎**。强制 calculator 那组，参数一共 12 段：

```
[02] tool_calls[0] id='call_00_gQIUkD5AE8tsLC5QRfOt7820' name='calculator' args=''
[03] tool_calls[0] id=None name=None args='{'
[04] tool_calls[0] id=None name=None args='"'
[05] tool_calls[0] id=None name=None args='expression'
[06] tool_calls[0] id=None name=None args='"'
[07] tool_calls[0] id=None name=None args=': '
[08] tool_calls[0] id=None name=None args='"'
[09] tool_calls[0] id=None name=None args='123'
[10] tool_calls[0] id=None name=None args=' *'
[11] tool_calls[0] id=None name=None args=' '
[12] tool_calls[0] id=None name=None args='45'
[13] tool_calls[0] id=None name=None args='"'
[14] tool_calls[0] id=None name=None args='}'
[15] finish_reason='tool_calls'
```

拼接后 `{"expression": "123 * 45"}`。**实现必须按 index 分段拼接，不能假设一整块到达**——
这是本次改造里最容易写错、也最值得测的地方。

另外三个观察：

- `id` 和 `name` 只在第一段给，后续段是 `None`
- `finish_reason='tool_calls'` 出现在一个 **delta 全空的 chunk** 上（第 15 个）
- 每个流以**空 delta** 开头（第 1 个 chunk），`delta` 本身不为 None，只是字段全是 None

### 2.3 `include_usage` 还有效吗

**有效**。带 `tools` 的流末尾照样有一个 `choices: []` + `usage` 的收尾 chunk，
所以空回复的 `reasoning_tokens` 诊断在流式工具路径上也没丢。

## 3. 设计：正文和「还要不要调工具」怎么一起传

流式调用有个天然的矛盾：

```
生成器一边往外 yield 正文，一边在等「模型还有没有话要说」。
但生成器的 return 值传不出去（yield from 拿不到子生成器的返回值），
所以「这一轮是最终答案还是要调工具」这个结论，没法随最后一个 yield 一起带出去。
```

解决方案是把**收尾信息作为一个片段本身**传出去：

```python
@dataclass
class StreamChunk:
    text: str = ""                    # 非空 → 该发给用户的一段正文，可能只有几个字
    finish_reason: str | None = None  # 非 None → 这一轮已收尾
    tool_calls: list[ToolCall] | None = None

    @property
    def ended(self) -> bool:
        return self.finish_reason is not None
```

正文片段和收尾片段走同一个流，调用方一眼能分清：

```python
for chunk in self._provider.complete_stream(cleaned, tools=schemas):
    if chunk.text:
        yield chunk.text          # 正文逐段往外吐
    if chunk.ended:
        tool_calls = chunk.tool_calls or []
        break
```

**为什么不把 `tool_calls` 也允许出现在正文片段里**：工具参数是分段拼接的，中途的片段
是不完整的 JSON，提前暴露给 agent 会导致「工具被执行两次」（第一段执行一次、拼完再执行一次）。
拼接收在 provider 层，agent 只在收尾片段看到完整结果，责任就只有一个地方。

### 4.1 为什么 `complete_stream` 不是 abstractmethod

`BaseProvider` 给的是一个**能跑的默认实现**——退化为非流式 `complete()`，把整段正文切成
16 字小块吐出（沿用删掉的 `_chunked(16)` 的节奏）。理由：

```python
    def complete_stream(self, messages, tools=None) -> Iterator[StreamChunk]:
        result = self.complete(messages, tools=tools)
        if result.tool_calls:
            yield StreamChunk(finish_reason="tool_calls", tool_calls=result.tool_calls)
            return
        for i in range(0, len(result.content), _STREAM_TEXT_SIZE):
            yield StreamChunk(text=result.content[i:i + _STREAM_TEXT_SIZE])
        yield StreamChunk(finish_reason=result.finish_reason)
```

改成 abstract 就得给 `tests/` 里每个假 provider 补方法，那些改动跟被测行为无关，是噪音。
留默认实现，**行为与改造前完全一致**，没覆写的 provider 只是拿不到流式收益。
测试里有 `test_base_default_complete_stream_keeps_plain_providers_working` 锁住这一点。

## 5. 逐行解读：反直觉的那几条

### 5.1 工具参数按 index 拼接，name 和 arguments 都可能分段

```python
for tc in getattr(delta, "tool_calls", None) or []:
    slot = pending.setdefault(tc.index, {"id": "", "name": "", "arguments": ""})
    if tc.id:
        slot["id"] = tc.id
    fn = tc.function
    if fn is not None:
        if fn.name:
            slot["name"] += fn.name
        if fn.arguments:
            slot["arguments"] += fn.arguments
```

三处防御，每处都对应一个真实到达形态：

- `getattr(delta, "tool_calls", None) or []` —— 老 SDK / 其他供应商的 delta 上可能没有
  `tool_calls` 属性（探针第 1、15 个 chunk 就是），直接 `delta.tool_calls` 会 AttributeError
- `if tc.id` / `if fn.name` —— id 和 name **只在第一段给**，后面是 None，不能覆盖成空串
- `fn is not None` —— 参数分段里 `function` 有值，但极端情况下可能整个缺

拼接完按 index 排序返回：

```python
tool_calls = [ToolCall(s["id"], s["name"], s["arguments"])
              for _, s in sorted(pending.items())]
```

排序是为了稳定。DeepSeek 会先给 index 0 再给 index 1，但不能假设所有供应商都这样
（并发多工具调用时段的顺序没有协议保证），排序后 agent 看到的结果与到达顺序无关。

### 5.2 空回复的判定要改

非流式时判空很简单：`content` 为空。流式工具路径上**只有工具调用、没有正文是正常的一轮**：

```python
if not total and not tool_calls:
    self._reject_empty(kwargs.get("max_tokens"), usage)
```

漏掉 `and not tool_calls` 会让每一次工具调用都抛 `EmptyReplyError`——那种 bug 测试一跑就红，
但它是最容易漏写的那半句，所以专门有
`test_complete_stream_tool_calls_count_as_a_reply` 锁住。

### 5.3 重试只在「一个字符都没吐」时做

```python
except Exception as exc:
    if emitted:
        self._breaker.record_failure(exc)
        raise                  # 已经吐过字了，重试会重复输出
    attempt = self._retry(exc, attempt, start)
```

这是流式引入的一个新边界，非流式时不存在：非流式失败就是失败，没东西泄露给用户；
流式已经往外吐了 30 个字，再重试会把同样的 30 个字**再吐一遍**，用户会看到重复内容。

所以选了「宁可直接失败」。但失败仍然记账（`record_failure`）——熔断器要知道上游不健康，
只是不该为了它重放已经吐出去的内容。

代价写在 §7.4：用户可能看到半截回复加一个错误。没有更好的选择。

### 5.4 收窄的是每次尝试，不是重试间隔

`_timeout_for(start)` 沿用 docs/15 的那套：read 超时按**距预算终点的剩余时间**收窄，
并且按单次请求传，不改 `self._client.timeout`（provider 是多会话共享的单例，改 client
属性会让并发会话互相踩）。`complete_stream` 复用同一个方法，四个入口（chat / complete /
chat_stream / complete_stream）的重试与预算口径仍然只有一份。

`test_complete_stream_honors_deadline` 锁住这条：预算耗尽抛 `DeadlineExceeded` 而不是
继续重试到把线程占住。

### 5.5 编码异常回退，且只记一次账

```python
except UnicodeError:
    comp = self.complete(messages, tools=tools)
    ...
```

流式解码遇到「多字节字符被网络切分」时回退非流式，保证对话可用（沿用 M8 的做法）。
回退那次调用由 `complete()` 自己做熔断检查与记账，这里**不再记一次**——同一个失败算两遍
会把熔断阈值提前触发，把一个偶发抖动升级成熔断。

### 5.6 为什么 `_chunked()` 直接删掉

`_chunked(16)` 是把「算好的整段答案」切成 16 字一段，假装逐段到达。现在最终答案本来就是
逐 token 到达的，再切一次没有意义，分段大小由服务端决定（实测单段 1~4 字）。

删掉而不是留着不用：留着会让人以为它还在用，而它存在的唯一理由（工具循环是非流式的）
已经不存在了。

## 6. 实测

`scripts/e2e_stream_tools.py`，`deepseek-chat`，同一天多次运行取中位附近的值：

| 问题 | chunk 数 | 总字符 | 首字耗时 | 答案轮时长 | 单段最大 | 平均间隔 |
| --- | --- | --- | --- | --- | --- | --- |
| 「123 × 45 等于多少」（要调工具） | 10 | 21 | 2.76s | 0.12s | 3 字 | 0.013s |
| 「用 20 个字介绍杭州」（无工具） | 15 | 23 | 0.93s | 0.23s | 3 字 | 0.016s |
| 「详细介绍西湖，写 400 字」（无工具） | 318 | 458 | 1.20s | 2.79s | 4 字 | 0.009s |

同一句「详细介绍西湖」走旧路径的对照：

```
complete()        : 1 个整块，383 字，耗时 2.75s（用户在开头等满这么久才看到第一个字）
complete_stream() : 318 个片段，共 458 字，首字 1.20s，单段最大 4 字
```

**判据**：一次性下发是「一个大 chunk + 后面全 0」，真流式是一连串小 chunk 且间隔可用。
脚本里按「段数 > 4 且首段占全文 < 50%」判真流式，三组都过了。

⚠ 引用这两个数字时不要写成固定值——网络抖动对首字耗时的影响比答案长度还大
（`docs/13` §7 发现一记过同样的事）。**稳定的结论是「长回复的首字提前了约一半」，
不是「首字 1.20s」。**

## 7. 还没修好的（诚实清单）

### 7.1 首字耗时没改善，甚至更慢（等待本身已给出提示，见 §10）

工具调用那一轮**不产出正文**，所以「首字耗时」里包含「模型想 + 调工具 + 再想」的完整时间。
改动前你在屏幕上看到的是「思考中 2.7s → 整段出现」，改动后是「思考中 2.76s → 逐字出现」。

**第一个字出现的时间一点没变，甚至因为工具 schema 参与 prefill 慢了约 0.4s**
（不带工具 0.74s，见 `docs/14`）。收益全部在答案轮：改动后答案逐字渲染，改动前是最后一刻整段落下。

所以这个改造**修的是「答案渲染方式」，不是「响应延迟」**。别在简历或文档里写成「降低延迟」。

**能改善的不是首字时间，是那段时间的体感**——已做，见 §10。

### 7.2 短回复看不出差别

21 字的答案轮只花 0.12s，0.12s 内一次性出现和逐字出现，人眼分不出来。
收益要到答案轮本身超过一秒才看得见（458 字那组 2.79s）。

### 7.3 半截回复 + 错误：后端没兜，但前端兜住了

见 §5.3：已经吐过正文之后失败就直接抛，provider 和 agent 层都不做任何补偿。

**后端确实不做补偿，但前端补了。** `static/index.html` 收到 `{"error": ...}` 事件时用的是
`aiBubble.textContent = '⚠️ ' + obj.error` —— 整体**替换**，不是追加。所以已经渲染出来的
半截正文会被错误消息覆盖，用户看到的是干净的报错，不是「半截话 + 一个错误提示」。

会话状态也干净：失败时 `service._send_locked` 会把本轮用户消息撤回，磁盘上不会留下
「问了一半答了一半」的记录。

**但这条正确性只靠一个赋值撑着** —— `textContent =` 而不是 `textContent +=` 或
`innerHTML +=`。哪天有人为了让用户看到「模型说到哪儿了」把它改成追加，这个行为就没了，
而且不会有任何测试变红（前端不在测试覆盖里）。记在这里，别改错。

### 7.4 商汤的流式 + 工具：已实测（2026-10-16）

`spike_stream_tools.py` 按 `LLM_PROVIDER` 自动选供应商，切到商汤跑了一遍。**能用，行为不一样，
但实现照样正确**：

| | DeepSeek | 商汤 flash-lite |
| --- | --- | --- |
| `stream=True` + `tools` | ✅ | ✅ |
| 工具参数 | **分 12 段到达** | **整块 1 段到达** |
| 最终答案 | 逐 token（318 段） | **整块 1 段** |
| 计算期的 chunk | 直接进正文 / tool_calls | **先吐一串空 delta**（6~8 个） |
| 参数 chunk 的 `id` / `name` | `None` | **空字符串 `''`** |

两个值得记的收获：

1. **§5.1 那几个真值守卫现在有第二个理由了。** 商汤给的是 `id=''` 而不是 `id=None`——
   代码里用的是 `if tc.id:` / `if fn.name:`（真值判断）而不是 `if tc.id is not None:`，
   所以 `''` 不会把已经拼好的值覆盖成空串。**当初若写成 `is not None`，商汤这里就崩了。**
2. **分段拼接对「整块到达」也成立**。一段就是全段的特例，不需要任何特殊分支。
   所以这个实现是**供应商无关的**，不需要为商汤加开关。

商汤上流式工具循环等于**没有流式收益**（最终答案还是一整块落下），但不会退化、不会出错。
之前那条「要切回去先跑一遍 spike」的建议现在可以删掉了——已经跑过。


### 7.5 `deadline` 不约束流式传输的中段

docs/15 §8.3 那条边界现在同样适用于 `complete_stream`：预算管的是
「从调用进入到第一次尝试失败为止」，一旦开始往外吐字，逐段间隔受 read timeout 约束、
不受 deadline 约束。要管住那一段得上看门狗线程，对话场景里不值得。

### 7.6 生产环境里 `chat_stream` 那条路其实是死路

工具始终注册，所以 `agent.respond()` 里的 `if not schemas` 分支在生产环境一次都进不去
（`docs/06` 已经点过这个现象）。保留它不是为了流式，是为了**降级场景**：
MCP 和 RAG 都不可用、且默认工具被去掉的时候，以及测试里注入无工具的 provider。
`test_agent_without_tools_still_uses_chat_stream` 锁住它还在工作。

分两组，**chunk 的对象形状不一样，别混**：provider 层喂的是 openai SDK 形状的 chunk

`tests/test_request_id.py` 里 `_ToolCallingProvider` 是个不继承 `BaseProvider` 的裸类
（刻意 duck-type），所以没吃到默认实现，给它补了一个同构的 `complete_stream`。
其余假 provider 都继承 `BaseProvider`，一行没改、全部仍然全绿——这就是 §4.1 那个决定的价值。

一条手法上的点：**流式失败发生在「已吐过字之后」这个分支没法用假 transport 测**
（自定义 BaseTransport 里的 sleep 触发不了 read timeout，见那条踩坑记录），
所以我用一个「yield 一次然后抛异常」的迭代器制造它——便宜，而且它测的正是「别再重试」这个决定。

## 9. 追加：工具进度提示（2026-10-16）

§7.1 说「首字不会更快」。那段时间能做的只有一件事：**告诉用户系统在干什么**。

### 9.1 为什么是一个新的事件类型，而不是复用 delta

工具轮没有正文，用户在那段时间里只能看到一个静止的「思考中…」。要在这段等待里给出
「正在计算…」这种具体信息，就必须在流里多一种东西。

它**不是回复内容**——不能进会话历史、不能进 CLI 输出、不能算进空回复检测。所以不能
伪装成 `delta` 发出去：那样它会被拼进 `reply`、写进磁盘上的会话 JSON，下次把历史发给
模型时就是一段假的「正在计算…」。

于是给它一个独立类型，并在唯一的分叉点过滤掉：

```
agent.respond()        → Iterator[str | AgentStatus]    产出事件流
service.send_events()  → 透传（status 排除在 reply 累积之外）
service.send()         → 过滤成 Iterator[str]           CLI / 测试用，行为不变
api.stream()           → 两种 SSE：{"delta": ...} / {"status": ...}
index.html             → delta 走 innerHTML 追加，status 走 textContent 整体替换
```

`send()` 保持原签名是刻意的：245 个旧用例和 9 个脚本全部不感知这次改动。
代价是 `tests/test_tools.py` 里有两处 `"".join(agent.respond(...))` 要显式过滤——
值得付，它强迫写测试的人知道这个联合类型存在。

### 9.2 两个真实的时序坑

**坑一**：最初把工具参数和收尾放在两个 chunk 上写测试，跑出来 `order == []`——工具
根本没执行。因为 `StreamChunk` 的契约是 **tool_calls 只在收尾片段给出**，而测试给的
收尾片段是 `StreamChunk(finish_reason="stop")`（`tool_calls=None`）。契约没错，测试写错了。

这个坑反过来验证了契约的价值：`respond()` **只在收尾片段读一次 tool_calls**，中途片段不读。
如果中途也读，同一个工具会被执行两遍（参数还没拼完时执行一次，拼完再执行一次）——
写文件、发消息这类工具有真实副作用。

**坑二**：想验证「提示在工具之前到达」时，不能用 `list()` 收集完再回溯，那样记出来的
顺序是 `[tool, tool, status, status]`。工具的副作用发生在生成器 `yield` 之后、调用方
恢复执行的那一刻，**只有按到达顺序记录才看得出时序**。测试里那条注释写着原因。

### 9.3 实测

真实调用 `deepseek-chat`：

```
  +0.00s  （请求发出）
  +1.41s  STATUS  '正在计算…'
  +2.29s  delta   '123'
  ...
  +2.41s  delta   '**'
```

历史落盘只有两条，干净的：

```
  user       '帮我算一下 123 × 45 等于多少？'
  assistant  '123 × 45 = **5535**'
```

**1.41s 那个位置，改动前是一行静止的「思考中…」**。用户不会更早看到答案，但他知道
系统在算 123×45，而不是程序死了。

### 9.4 四个刻意的决定

1. **工具执行前才发提示**。`respond()` 里 `yield AgentStatus(...)` 在 `execute(...)` 之前
   一行——顺序反了，用户会看到「正在计算…」但工具其实早跑完了。
2. **每个工具发一次**。一轮里调两个工具就发两条。前端用 `textContent =` 整体替换，
   所以不会叠加成一行乱码。
3. **CLI 不显示提示**。CLI 走 `send()`，提示被过滤掉。终端没有「气泡」概念，加一行
   会污染对话文本；真要做应该走 stderr 且只在 `-v` 时开。
4. **工具卡住没有单独提示**。上限由 provider 的 `DEADLINE`（30s）兜住，超时抛
   `DeadlineExceeded` → SSE 发 error 事件 → 前端干净替换。最坏情况是等 30s 看到报错，
   不会无限挂着。

## 10. 小结

这次改动的净收益是一句话：**答案渲染从「最后一刻整段落下」变成「从第一个字开始逐字出现」，
长回复的首字提前了约一半**（2.75s → 1.20s 那一组的实测）。

加上 §9 的进度提示之后，多了一条：**工具轮那段 1.4s 的空白从「静止的思考中…」变成
「正在计算…」**——不能让用户更早看到答案，但能让用户知道系统在干什么。

更实质的收获是分清了两件一直混在一起的事：

| 问题 | 改造前怎么记 | 现在怎么记 |
| --- | --- | --- |
| 首字要等多久 | 一个「响应延迟」 | **工具轮耗时**（想 + 调工具 + 再想，改造管不到）<br>+ **首字耗时**（改造也管不到） |
| 答案怎么出现 | 一次 | 逐 token（**这次改的**） |
| 工具决定 | 和正文一起返回 | 每轮收尾时读出（正文不等它） |

两处反直觉的地方最值得记住：**工具参数是按段到达的，必须按 index 拼接**（不然工具拿到的
是半截 JSON，参数解析出来是空 dict，然后工具静默返回默认值），以及
**已经吐过字就绝对不能重试**（重放会让用户看到同一段话两遍）。第一条是探针跑出来的
（12 段 `{'` `"` `expression` …），不是从文档里读到的。
